# SpaceBadger — implementation plan

Derived from [`spacebadger-implementation-brief.md`](../spacebadger-implementation-brief.md), which remains the product specification. This plan records the architecture decisions, platform strategy, and milestone sequence. Update it when a decision changes.

## Environment baseline (2026-10-08)

| Item | State |
|---|---|
| Rust | 1.97.1 (MSVC), pinned in `rust-toolchain.toml` |
| Tauri | 2.12.x (latest stable; 3.0 is still alpha and not used) |
| Frontend build | Node 26 / npm 11, build-time only; the installed app has no Node runtime |
| Windows validation | Windows 11 + NTFS + OneDrive available on the dev machine |
| Linux validation | Docker Desktop only (no WSL distro): good for scanner probes and bind mounts, not for the desktop app |
| macOS validation | No machine available yet; CI build only until a real Mac with iCloud Drive is available |

## Architecture

| Area | Decision |
|---|---|
| Workspace | Cargo workspace: `crates/sb-core` (model, aggregation, search, layout), `crates/sb-scan` (traversal + per-OS adapters), `crates/sb-protocol` (versioned IPC types), `crates/sb-probe` (correctness-probe CLI), `src-tauri` (desktop bridge), `ui/` (Svelte 5 + TypeScript + Vite, canvas treemap). `sb-bench` is added in milestone 5. |
| Type sharing | IPC types live in `sb-protocol` and are exported to TypeScript with `ts-rs` into `ui/src/lib/protocol/`. A test fails if the generated bindings are stale. (`tauri-specta` for Tauri 2 is still a release candidate, so it is not used.) |
| Data model | Struct-of-arrays keyed by `u32` NodeId: parent, first-child, next-sibling, name offset into a byte arena (native names), logical `u64`, allocated `u64` with an unknown sentinel, file identity, flags. Full paths are reconstructed on demand. Target ~60 B/node + names, so 5M nodes ≈ 300 MB + names. |
| Scanner | Bounded directory-worker pool (smaller for network roots) → batches → a single aggregator thread that owns the model and propagates ancestor sums incrementally. Every scan has a generation ID; cancellation is an atomic flag checked between OS calls. |
| Streaming | The backend emits a coalesced progress/dirty event every ~150 ms. The UI then **pulls** the layout for the current viewport, which gives natural backpressure. The full tree is never sent. |
| Layout | In Rust, viewport-scoped: squarified treemap with depth and pixel thresholds and an "Other small items" aggregate. Returned as a compact binary rect list. Sibling order is re-sorted only when sizes change past a hysteresis threshold, plus a final relayout on completion. Hit testing is done in the UI against the returned rects. |
| Search | A backend overlay over the model with its own match aggregates, maintained incrementally as files arrive and tagged with a query revision so stale results are dropped. The result list is virtualized. |
| UI | Canvas for the treemap; standard accessible DOM for the toolbar, breadcrumbs, details panel, search results, and status bar. |

## Platform metadata strategy (highest risk)

- **Windows:** enumerate with `NtQueryDirectoryFile` + `FileIdExtdDirectoryInformation`, which returns EndOfFile, AllocationSize, attributes, reparse tag, and file ID per directory batch without opening files (fast and non-hydrating).
  - *Probe:* is directory-entry AllocationSize accurate versus `GetCompressedFileSizeW` for sparse, compressed, and OneDrive placeholder files? Directory entries are known to be stale in some cases.
  - *Probe:* the link count isn't in directory info. Is opening a file with `FILE_READ_ATTRIBUTES | FILE_FLAG_OPEN_REPARSE_POINT` safe for placeholders (no hydration)?
  - Reparse tags by category: symlink and mount-point (junction or volume mount) are skipped and counted; cloud tags are measured; unknown directory tags are skipped and reported.
- **Linux:** `getdents` plus `statx`/`fstatat` with `AT_SYMLINK_NOFOLLOW`. Allocated bytes = `st_blocks × 512`. Mount boundaries come from `STATX_ATTR_MOUNT_ROOT` or `stx_mnt_id`, falling back to `/proc/self/mountinfo`, so same-device bind mounts are caught. Hard links are tracked by `(dev, ino)`.
- **macOS:** `getattrlistbulk` provides allocated size, data length, file ID, link count, flags, and mount status. Set `IOPOL_MATERIALIZE_DATALESS_FILES` to "off" for the scan threads. Identify cloud-only files by `SF_DATALESS`.
  - *Probe:* `/` scanning across the system/data volume split and firmlinks.
- **Show in file manager:**
  - Windows: `SHOpenFolderAndSelectItems`.
  - macOS: `NSWorkspace activateFileViewerSelectingURLs`.
  - Linux: `org.freedesktop.FileManager1.ShowItems` over D-Bus, falling back to opening the parent folder with structured arguments, never through a shell.
  - `tauri-plugin-opener` 2.7.0's `reveal_item_in_dir` does all three (Linux falls back to the OpenURI portal's `OpenDirectory`), so it is used from Rust.

## Milestones

0. **Baseline** — pinned toolchain and dependencies, workspace skeleton, minimal Tauri window, shared protocol bindings, CI on Windows, Linux, and macOS (fmt, clippy, tests, UI type-check, app build).
1. **Correctness probes** — `sb-probe` CLI reporting length, allocation (by every candidate API), file ID, link count, reparse tag or flags, and hydration state before and after.
   - Windows fixtures: sparse (`fsutil sparse`), compressed (`compact /c`), hard links (`mklink /H`), junctions, symlinks, and OneDrive files in their three states (online-only, locally available, always keep).
   - Linux fixtures, in Docker: sparse files, bind mounts, symlink loops.
   - Output: a results table in `docs/validation/`, with unsupported cases listed explicitly.
2. **Scanner core** — scoped traversal, stable identities, both metrics, omission aggregation by reason, batching, cancellation. Tested with fixture trees and a fake-filesystem adapter, no window needed.
3. **Streaming desktop slice** — root picker, live provisional treemap, select/zoom, breadcrumbs, cancel with retained partial results.
4. **Usability** — filename filter and results list, details panel, reveal, refresh, color modes, empty and error states, optional volume overview strip.
   - **Unattributed space block.** At a whole-volume root, in allocated mode, with no filename filter, and only after a completed scan: one block sized as volume used (capacity − free) minus scanned allocation. It's labelled as a non-file region and opens a breakdown of likely contributors (permission-denied folders with counts and samples, filesystem metadata, shadow copies, alternate data streams, other overhead). During a scan or after cancel, the gap includes unscanned files, so the block isn't shown.
   - **Elevated scans (scanner side, early milestone 3).** Never auto-elevate (on Windows the user can ask to restart elevated; see the 2026-10-13 decision). When the process already runs elevated:
     - Windows: enable `SeBackupPrivilege` and open directories with `FILE_FLAG_BACKUP_SEMANTICS` so protected folders (`System Volume Information`, `Config.Msi`, other users' recycle bins) list normally, which also surfaces shadow-copy storage.
     - Windows: query NTFS metadata sizes (`FSCTL_GET_NTFS_VOLUME_DATA` for MFT valid length, plus the change journal) and show them as items in a "Filesystem metadata" block.
     - Alternate data streams stay opt-in ("measure alternate streams"), because per-file stream queries are ~6.5× slower (milestone 1). Raw MFT reading is a separate later decision.
     - Linux/macOS: running as root removes most permission-denied omissions; filesystem overhead (e.g. ext4 reserved blocks) stays in the residual block.
   - Whatever remains after measured contributors is shown as "other filesystem overhead", never distributed into folders.
5. **Scale and packaging** — `sb-bench` with 1M and 5M synthetic plus real fixtures, memory/IPC/layout tuning, README, validation report. Packaging moved to milestones 7 and 8.
6. **Selection and delete** (added at the user's request; the brief left deletion out of the first version) — select several files and folders with Ctrl/Shift clicks, then move them to the Recycle Bin or Trash behind explicit protections: off until allowed for the session, typed confirmation, never permanent. Deleted items leave the scan without a rescan.
7. **Portable releases** — MIT license, portable downloads for Windows x64 (zip), Linux x86_64 (AppImage), and macOS Apple Silicon (zipped app), each with third-party license notices. Releases are cut on a `release/vX.Y.Z` branch from `dev`, which is built and tested on every push, merged into `main`, tagged there to publish, and merged back into `dev`. No installers. Process: [`docs/RELEASING.md`](RELEASING.md).
8. **Package managers** — Chocolatey and winget from the Windows zip; a signed apt repository serving a `.deb`; a Homebrew tap. Official Homebrew and Debian archives are out of reach for now (notarization and notability; Debian's build-from-source rules).
9. **Interface pass** (at the user's request) — a UI/UX review and cleanup: shared design tokens and styles, grouped toolbar, tabbed side panel, shortcuts sheet, one keyboard-driven list for results and small items, a modal delete dialog with a result screen, plain-language omissions, and screen-reader announcements limited to finished events. Evidence: [`docs/validation/ux-m9.md`](validation/ux-m9.md).

- 2026-10-09: Deletion added (milestone 6) although the brief excluded it from the first version, at the user's request. Because it can be heavily destructive, the user asked for explicit protections: deleting is off until turned on for the current run (enforced in the backend too), the confirmation needs `delete` typed after a 3-second countdown, and there is no permanent delete. Windows recycles through `IFileOperation` with a progress sink that aborts any item the shell wouldn't recycle (network/removable drives, oversized items, recycling off), so the shell's silent fallback to permanent deletion can't happen; macOS and Linux use the `trash` crate 5.2.9, which always keeps a copy. Only after the scan finishes or is cancelled. Each item is re-checked against the scan (same kind, not a link) and counts as deleted only once it is gone. Deleted nodes are removed from the tree in place (sizes taken off their ancestors, a removed hard-link owner hands its allocation to a remaining alias) and published as a new scan revision. The layout format (version 3) now sends each rectangle's parent folder, for Shift ranges. Evidence: [`docs/validation/delete-m6.md`](validation/delete-m6.md).

Evidence: [`docs/validation/filter-patterns.md`](validation/filter-patterns.md).

- 2026-10-13: Interface pass (milestone 9). The user cares about file size, not size on disk, so the interface measures logical size only: the Allocated/Logical switch is removed and the in-map unattributed-space block (allocated-only) is no longer drawn; the volume overview keeps comparing allocated space against disk usage, and the protocol still offers both metrics. The side panel pins the details and shows one list at a time as tabs. Evidence: [`docs/validation/ux-m9.md`](validation/ux-m9.md).
- 2026-10-13: Restart as administrator, at the user's request, replacing "the app never elevates itself" (2026-10-08). It is still never automatic: on Windows, when not elevated, a toolbar button (and one beside "Permission denied" under Not counted) asks for confirmation, then relaunches the program through the UAC prompt (`ShellExecuteExW` with `runas`) with the scan root as its argument and exits. Declining either prompt leaves the running copy as it was; it's refused while a delete runs. Allow deleting starts off again in the new copy. Not offered on Linux or macOS, where a root webview would be the wrong tool.
- 2026-10-13: Folder patterns in the filter, at the user's request: a `dir:` prefix matches folder names (same wildcards, any case); a file matches only inside a matching folder at any depth below the scan root (the root's own name never counts), and `!dir:` leaves out files inside matching folders. Folder patterns narrow file patterns rather than adding to them (`dir:node_modules; *.js` is JavaScript inside `node_modules`), so totals still count only matching files. Chosen over making plain patterns match folders, which would mix two meanings of a match. The search keeps one byte per node for folder scope, filled in the same ID-order pass; 5M synthetic nodes search in 316 ms for `dir:a` against 186–339 ms for file queries.
- 2026-10-13: Export, at the user's request: a folder's contents or everything under it as CSV or a plain-text report, saved where the user chooses in the native save dialog (`tauri-plugin-dialog`, no JavaScript permission). The backend writes the file, never the webview, in steps of 50,000 items: each step takes the search mutex (only when filtered) and the tree read lock only to format its rows into a buffer, which is written with the locks released, so a running scan isn't held up and memory stays bounded (a full snapshot would cost as much as the tree's paths). The walk keeps a stack of node IDs across steps and skips nodes removed meanwhile; an export taken while scanning is a partial picture, like the map, with each row's share taken against the folder's size at its step. With a filter, rows are matching files and the folders containing them, with matching totals; a filter with different text stops it (the same text applied again doesn't), and so does a new scan, checked between steps. CSV is RFC 4180 with a UTF-8 BOM and CRLF, sizes as byte integers plus a display column, and a leading `'` on text starting with `=`, `+`, `-`, `@`, tab, or CR against formula injection. The file is written as `.<name>.partial` beside the target and renamed over it only when complete, so a failed export leaves an existing file intact. The save dialog's suggested name is reduced to a plain file name with the format's extension in the backend. Writing lives in `sb-core::export`, the stepping in the session.
- 2026-10-13: File types and completion in the filter, at the user's request. `is:<type>` uses the file-type color categories (video, audio, image, document, archive, diskimage, program, code, other); the user chose the `is:` prefix, like `dir:`, over bare words such as `isVideo`, which would collide with name search. An included type counts like an included name pattern and `!is:` excludes; any unambiguous start of a type works, so a half-typed `is:vid` already searches, and an unknown or ambiguous type is reported inline. Completion follows the term at the caret: keywords, types, folder names after `dir:`, and extensions after `*.`. Names come from an index of the scan (grouped ignoring case, ranked by size, nested same-named folders counted once, at most 100,000 folder names), cached per scan revision and rebuilt at most every five seconds while scanning (431 ms for 5M synthetic nodes with 745,000 distinct folder names; a fast hasher and selecting the kept names before sorting brought it down from 1.56 s).
- 2026-10-13: Size and age terms in the filter, at the user's request: `size:` (`>`, `>=`, `<`, `<=`, or an inclusive `a..b`, with KB as 1,024 bytes on Windows and 1,000 elsewhere, matching the interface) compares logical size, and `older:`/`newer:` (a duration in `h`, `d`, `w`, `mo` = 30 days, `y` = 365 days, or a `YYYY-MM-DD` date from local midnight, counted from when the filter is applied) compare the modified time. They restrict rather than match: all must hold, on top of the name, type, and folder rules, and `!` negates one; files with an unknown modified time never pass an age term, negated or not. Because a size can change after a file is first examined (hard-link re-measures), a query that depends on size (size terms, or `is:` types, since `.ts` depends on size) re-matches changed files, which can join or leave the matches. To support age, the scanner now records modified times from the listings it already reads (`LastWriteTime` on Windows, statx `mtime` on Linux, `lstat` elsewhere), and the tree stores them as `u32` seconds since the Unix epoch (0 unknown, clamped to 1970–2106; the details leave clamped times out, and dates before 1970 aren't told apart): 4 bytes per node. Local midnight comes from `chrono` (clock feature only, already in the lock file through Tauri) in the app, passed to `sb-core` as a resolver so the core stays dependency-free. On 1M synthetic nodes the tree estimate goes from 70 to 74 MiB, peak working set from 150 to 153 MiB, and build time is unchanged within noise (334–448 ms before, 348–355 ms after); on 5M, 456 to 488 MiB estimated (rounded up by vector capacity) and 754 to 774 MiB peak. Search times are unchanged.
- 2026-10-13: Comparing with an earlier scan ("what grew?"). When a scan completes (never a cancelled or failed one), a background thread saves a snapshot to `snapshots/<hash of the absolute root path>/<finish ms>.sbsnap` in the app's local (not roaming) data folder, written to a temporary file and renamed into place. The format (`sb_core::snapshot`, version 1) is a magic/version header that can be read alone for listing, then every folder (parent distance, name, logical size, file count, whether its contents were read) and every file of at least 1 MiB (name, size) as varints, then an FNV-1a checksum; damaged or truncated files are errors, never panics. Smaller files leave only a 32-bit hash of their name in their folder: a file that was small and is now over 1 MiB counts as grown by at least the difference, one still small says nothing, and an unknown name is new. A folder unread then or now (permission denied) is unknown, and one with unreadable entries (the scanner now flags its listing) calls nothing inside it new or removed, with nothing new or removed inside it. No compression or new dependency: the user's 1.34M-file profile makes 10.2 MiB (capture 96 ms, write 24 ms) and the 3.66M-node `C:\` 31.7 MiB (capture 433 ms, write 170 ms, read 184 ms, match 581 ms). Retention per root: the newest 5, the first of each earlier day (UTC), and always the first, so repeated rescans don't push out the baseline; then the oldest go until all fit 256 MiB, daily ones first and a root's first last. Matching is by path relative to the root, one folder's children at a time (sorted names, binary search), ignoring case on Windows and macOS by per-character upper-casing of BMP characters like NTFS, exact names winning over names equal only ignoring case; a rename is removed plus new. The match is one `u32` per node, cached per comparison and rebuilt off the lock when the scan revision changes (deletes). Comparing needs a completed scan and carries over a rescan of the same root, holding the snapshot in memory and protecting its file from pruning; the change colors come from a separate per-layout request, so the layout wire format is unchanged.
- 2026-10-13: Finding duplicate files, at the user's request: the one feature that reads file contents, which the brief otherwise rules out. It runs only when the user asks, for the folder in view and the files the filter matches, and never reads cloud files: those flagged in the scan are counted and skipped, and on Windows each file is first opened for attributes only and refused if it carries a recall or offline attribute or isn't a plain file of the scanned size, then read with `OPEN_NO_RECALL` and `OPEN_REPARSE_POINT` as the same file (by file ID). Files behind any other reparse point (dedup, SIS, HSM, ProjFS) are refused, since a raw read would give their stub, not their contents; WOF-compressed files show no reparse point to callers and read normally. On Linux the open uses `O_NOFOLLOW | O_NONBLOCK` (and `O_NOATIME` where permitted), on macOS the same flags plus a check that the opened file is the one examined. Only the file itself is guarded against having become a link: a folder above it swapped for a link after the scan isn't detected. Candidates share their size with another file; a hard-linked file counts once, by its first name where that's a candidate and otherwise by another of its names, and copies with other names are marked. Groups are split by a BLAKE3 hash (the `blake3` crate, CC0/Apache-2.0) of the first and last 64 KiB, then confirmed by a hash of the whole file, most space at stake first. Work is handed out a file at a time to six readers, since opening is the slow part (virus scanning) and one large group shouldn't run on one thread, but only two read large files whole at a time, for spinning disks and shares. Before a delete, the dialog warns if a group would lose every copy, checking on disk that the copies meant to stay are still there at the compared size. Results stay with the scan, skip deleted files, and are replaced by the next search. On the benchmark machine: 13.4 GB of large same-size files read in 18 s (768 MB/s), and 117,000 small same-size files in `C:\Program Files (x86)` checked in 144 s cold (about 800 files/s, against 150–300 with two readers) and 13 s warm.
- 2026-10-13: Package managers, Windows first (milestone 8). winget (`StevenPickles.SpaceBadger`, a portable app inside the release zip, schema 1.10.0) and Chocolatey (`spacebadger`, downloading the zip rather than embedding it) are generated from templates with the version and the checksum from the release's `SHA256SUMS`. A packages workflow, called by the release workflow after publishing, attaches them to the run and submits them only when `WINGET_TOKEN` or `CHOCO_API_KEY` is set; the first versions are submitted by hand for review. The apt repository and Homebrew tap remain for later.
- 2026-10-13: Deletes bound to the scanned object, after a code review showed a file replaced after the scan could be recycled in its place (only the final component's kind was checked). The scanner now keeps an 8-byte ID per node: a fingerprint of the listing's file ID on Windows (128-bit from `FileIdExtdDirectoryInfo`, or 64-bit from `FileIdBothDirectoryInfo`; exact for IDs that fit 64 bits, the high half mixed in otherwise) or of the inode number elsewhere (the scan never crosses devices; the device is checked at delete time against the root's, read when the scan starts). Cost on the benchmark: tree estimate 74 → 82 MiB at 1M nodes and 488 → 552 MiB at 5M, peak working set 154 → 162 MiB and 772 → 812 MiB; a full 128-bit ID or a per-node device was judged not worth twice that. Just before each move, the scan root, every folder below it down to the item, and the item are opened without following reparse points (`CreateFileW` with `OPEN_REPARSE_POINT | BACKUP_SEMANTICS | OPEN_NO_RECALL`, attributes only; `lstat` elsewhere) and must match: kind and not a link, drive, ID (either the `FileIdInfo` 128-bit ID or the `GetFileInformationByHandle` 64-bit index, so both listing classes match), and for files size and modified second. A node the scanner had no ID for is checked on the rest. On Windows the folders are held open without delete sharing for the move, which blocks renaming or replacing them and doesn't stop the shell (tested), and the item is held with full sharing so that afterwards `GetFinalPathNameByHandleW` shows whether it reached `\$Recycle.Bin`, moved elsewhere (whatever replaced it went instead), or was deleted outright (NTFS parks a file deleted while open in `\$Extend\$Deleted`). Residual risk: the shell and the `trash` crate move by path, so an item swapped in between the check and the move can still go; on Windows that is detected and it is in the Recycle Bin, on macOS and Linux it isn't detected. Outcomes are now separate in the protocol (recycled, already missing, changed, failed, uncertain): an error is never dropped because the item is gone, Windows' "deleted without a copy" outranks every other result, and missing items are never counted as recycled. Recycled, missing, and uncertain items leave the tree. The dialog gives the content (logical) size and "frees up to" the allocated size only when no file's allocation is unknown and none is hard-linked (the selection summary walks the items for hard links only when the scan found any); Windows listings can't see hard links outside the scan, hence "up to". After review: absolute paths are opened as `\\?\` paths without `GetFullPathNameW`, which drops a trailing dot or space and would read a different item (or none, misread as already missing); names ending with either are refused on Windows, since the shell parses them that way too. Only a folder just held being without the next name counts as already missing; a missing scan root or any other error is a failure. "Deleted without a copy" is uncertain whatever is left at the path, and only what's gone leaves the tree. Hard-linked files skip the modified-time comparison (NTFS keeps it stale for names not written through). Linux (`statx` `BTIME`, same call) and macOS (`st_birthtime`) IDs include the birth time in whole seconds above the inode number, so a reused inode number doesn't match; the delete side accepts the ID with or without it, for scans made where it wasn't available. Folders without any recorded ID are refused ("can't be confirmed to be the one scanned") rather than passed on kind and drive alone; files without one still go by size and modified time.
- 2026-10-14: Exclusive temporary files for exports and snapshots, from a code review. Both used to write a fixed name beside the target (`.<name>.partial`, `<id>.tmp`) with a truncating create, so an existing file or link at that name could be overwritten or written through, and two exports to one file shared it. Now `atomic_file::TempFile` (std only, no new dependency) creates `.<name>.<pid>-<random>.partial` in the target's folder with `create_new` (O_CREAT | O_EXCL, which refuses any existing name, links included; on Windows CREATE_NEW plus `FILE_FLAG_OPEN_REPARSE_POINT`), trying another name if it's taken. The handle stays open through the final rename (Windows allows renaming a file opened with delete sharing), so a temporary file that is discarded or fails to rename is removed only if it's still ours: through the handle (`FileDispositionInfo`) on Windows, and elsewhere only while the name still refers to the same device and inode. The rename replaces a target that is itself a link with the new file, as renaming does. Concurrent exports to one file each finish, the last rename winning. The snapshot store's prune removes `.partial` (and old `.tmp`) files over an hour old, so crash leftovers go and saves in progress don't. The temporary name keeps at most the first 64 bytes of the destination's name, so names near the 255-character limit still work, and a refused rename (usually a file open elsewhere) is reported as possibly open in another program or read-only.
- 2026-10-14: Revalidating duplicates before a delete relies on them, after review found a same-size edit of the copy meant to stay passed the size check. Each file read whole is fingerprinted (file ID, or device and inode; length; modified time; number of names) through its handle as opened and again after reading, and a file written to in between is skipped as changing. Groups keep their BLAKE3 contents hash and each file's fingerprint. The delete dialog's check now compares fingerprints, not size, and says it is provisional. As the delete starts, before anything moves, only group members selected themselves (as from the Duplicates tab) are protected: members inside a selected folder go with it, so a folder delete never reads or keeps anything for duplicates. Each protected file is examined (fingerprint only) and kept if it changed since compared; then each such group's kept copies are held and read again in full through the same safe open (cloud and reparse rules unchanged) by a pool of six readers, at most two large files at once, trying a group's next copy only when one doesn't match fingerprint and hash. A protected file of a group with none confirmed is kept with a per-file failure naming it and saying why (it changed, the copies changed, unreadable, or stopped). Holding means, on Windows, opening the copy for reading while sharing only reading, before it's read and until the moves finish, so a confirmed copy can't be written, replaced, renamed or deleted in between; a copy another program has open to write can't be held and counts as unknown. Other systems have no such lock and only check. Unknown is never treated as proof, and a panic while reading keeps every protected file. Progress goes out as `duplicates-recheck` events and the dialog can stop it. Groups losing every file are not rechecked: the dialog warned and the user confirmed. Reclaimable space is shown as content (length) in the extra copies; an on-disk estimate (allocated sizes less the smallest copy) only where every copy's allocation is known and the link count read with it is one, labelled "up to", since block cloning and deduplication can share storage. Known gaps: off Windows a kept copy changed between its recheck and the moves isn't detected, and a writable mapping made before the hold isn't stopped by it.
- 2026-10-14: Directory listings stream in bounded batches, after a review found one very wide folder could spike memory and hold the tree's write lock for its whole listing. `FsAdapter::read_dir` hands at most 4,096 entries at a time to a sink (which can stop the listing), so the channel bounds entries rather than directories, and the aggregator locks the tree per batch and checks for a cancel between batches. A folder is `Listed` only after its last batch; one whose listing fails part way keeps what was read and is marked as having unreadable entries (not fully listed, so comparisons treat it as partial, and the map and details show it as partly read); one stopped by a cancel ends as not scanned, and the scan reports Cancelled even when that was its last work. The hard-link owner map is never grown with the lock held. On a synthetic 5M-entry folder, peak memory goes from 1,207 to 633 MiB, the longest reader wait from 1.4 s to 41 ms (the tree's arrays doubling), and a cancel during aggregation from 1.5 s to 3 ms; ordinary trees scan at the same speed. Evidence: [`docs/validation/wide-dirs.md`](validation/wide-dirs.md).
- 2026-10-14: The layout orders only the children it draws, from an architecture review. Whether a child is merged into "other small items" depends only on its own weight (its area, weight × rect area ÷ folder weight, is below `min_area`), so `fill` now sums the invisible children in one pass and sorts only the rest, of which there can be no more than the area over `min_area`; final layouts are unchanged, which randomized tests check against the previous implementation kept as a test-only reference. The order cache remembers only drawn children, as sorted (child, rank) arrays at 8 bytes each, and is bounded at 2^20 children in all rather than 100,000 folders, evicting the least recently used folders; an order larger than the whole budget isn't kept. While scanning, the reorder hysteresis now compares drawn siblings only: invisible files arriving or changing order no longer force a full re-sort of the visible ones (they used to whenever a new tiny file was 1.5× the smallest known one), and a child that was too small to draw last time is placed as a new one. A folder of 5M equal files lays out in 8–9 ms instead of 0.5–0.7 s, and its cached order drops from 72 MiB to nothing. Evidence: [`docs/validation/layout-lod.md`](validation/layout-lod.md).
